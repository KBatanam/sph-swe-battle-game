# Compute Shader移植方針

## 基本方針

現在のManaged C#版を、理論と計算結果を確認するためのCPU基準実装として保持する。大規模粒子向けの実ゲーム用シミュレーションは、Compute Shader版として別に実装する。

```text
CPU基準実装
├─ 小規模な正解確認
├─ カーネルと密度計算のテスト
└─ GPU版との結果比較

Compute Shader実装
├─ 大規模粒子シミュレーション
├─ GPU上で近傍探索、密度、加速度および積分を実行
└─ GPUバッファから直接描画
```

BurstおよびJob SystemはCompute Shader移植の必須条件ではないため、現在は経由しない。

## 移植手順

1. CPUとGPUで共有する粒子データのメモリレイアウトを定義する。
2. CPU粒子をGPU用粒子へ変換する。
3. `GraphicsBuffer`を使用してGPUへ転送する。
4. 最小のCompute Shaderで粒子データをコピーする。
5. 一度だけCPUへ読み戻し、全フィールドが一致することを確認する。
6. GPU空間グリッドを実装する。
7. GPU密度計算を実装し、CPU版と比較する。
8. GPU加速度計算を実装し、CPU版と比較する。
9. GPU時間積分を実装する。
10. CPUへの毎フレームの読み戻しを廃止し、GPUバッファから直接描画する。

## GPU粒子構造

GPU転送専用の`SphSweGpuParticle`をCPU基準実装の`SphSweParticle`とは別に定義する。

| フィールド | 型 | オフセット | サイズ |
|---|---|---:|---:|
| `Position` | `Vector2` / `float2` | 0 | 8 bytes |
| `Velocity` | `Vector2` / `float2` | 8 | 8 bytes |
| `Acceleration` | `Vector2` / `float2` | 16 | 8 bytes |
| `Density` | `float` | 24 | 4 bytes |
| `Mass` | `float` | 28 | 4 bytes |
| `InitialMass` | `float` | 32 | 4 bytes |
| `EffectiveRadius` | `float` | 36 | 4 bytes |
| `FluidDepth` | `float` | 40 | 4 bytes |
| `Type` | `int` | 44 | 4 bytes |

```text
Vector2 × 3 = 8 × 3 = 24 bytes
float   × 5 = 4 × 5 = 20 bytes
int     × 1 = 4 × 1 =  4 bytes
                       --------
                       48 bytes
```

C#側では`LayoutKind.Sequential`によりフィールドの記述順を維持し、`Pack = 4`により4バイト単位の配置を明示する。

フィールドの型、順序または個数を変更する場合は、C#側の`Stride`、HLSL側の構造体、およびレイアウトテストを同時に更新する。

## 読み戻しに関する方針

GPUからCPUへの読み戻しは同期または遅延を発生させるため、実ゲームの毎フレーム処理には使用しない。

初期実装ではデータレイアウトと計算結果を検証するためにだけ読み戻す。検証完了後は、GPU計算結果をGPU上に保持して描画へ直接使用する。

## GPU粒子レイアウトテスト

`Marshal.SizeOf<SphSweGpuParticle>()`による構造体サイズと、`Marshal.OffsetOf`による各フィールドの先頭位置を検証する。

2026年9月16日時点で、構造体サイズが48 bytesであり、各フィールドが設計どおりの位置へ配置されていることをUnity Editor上で確認した。

## 最小コピーCompute Shader

SPH-SWEの計算を移植する前に、GPUへ送った粒子を別のバッファへそのままコピーするカーネルを作成する。

この段階では物理量を変更しない。次の項目だけを独立して検証する。

- C#とHLSLの粒子構造が一致していること
- `GraphicsBuffer`のstrideが48 bytesであること
- 粒子数からスレッドグループ数を正しく求められること
- GPUへ転送した全フィールドを正しく読み戻せること

スレッドグループ当たりのスレッド数を64とする場合、必要なグループ数は次式で求める。

```text
threadGroupCountX = (particleCount + 64 - 1) / 64
```

除算結果を切り上げるため、最後のグループには粒子数を超えるスレッドが含まれる場合がある。そのため、Compute Shader側では`particleIndex >= particleCount`を判定して処理を終了する。

### コピー検証結果

2026年9月16日時点で、値の異なる2個のテスト粒子を使用し、次の経路で全フィールドが変化せずコピーされることをUnity Editor上で確認した。

```text
C#配列
  ↓ GraphicsBuffer.SetData
GPU入力バッファ
  ↓ CopyParticlesカーネル
GPU出力バッファ
  ↓ GraphicsBuffer.GetData
C#結果配列
```

これにより、C#とHLSLの粒子構造、48 bytesのstride、バッファ接続、Dispatch、および読み戻しが正常に機能していることを確認した。

## GPU空間グリッド

GPU版でもCPU基準実装と同様に、粒子を一様な格子へ登録して近傍候補を限定する。

```text
1. セルごとの粒子数を初期化
2. 各粒子が所属するセルを計算
3. セルごとの粒子数を集計
4. 各セルの粒子格納開始位置を計算
5. 粒子インデックスをセル順に並べる
6. 周辺セルから近傍粒子を探索
```

複数の粒子が同じセルへ同時に登録される可能性があるため、粒子数の集計には`InterlockedAdd`によるアトミック加算を使用する。通常の加算では、複数スレッドが同じ更新前の値を読み取り、片方の加算結果が失われる競合状態が発生する可能性がある。

一方、セル粒子数の初期化では1スレッドを1セルへ対応させる。各スレッドの書き込み先が異なるため、初期化にはアトミック操作を必要としない。

### GPUグリッドの範囲

CPU基準実装は、現在の全粒子からセル座標の最小値と最大値を毎回求めてグリッド範囲を決定する。

GPU版では、流体粒子がシミュレーション領域内に制限され、境界粒子の配置範囲も既知であることを利用し、シミュレーション領域と境界層を包含する固定グリッドを使用する。これにより、毎サブステップの最小値・最大値の並列リダクションと、その結果を使用する前のGPU同期を省略する。

各粒子について、グリッド内のローカルセル座標を次式で求める。

```text
localCellCoordinate = floor(
    (particlePosition - gridMinimumPosition) / gridCellSize
)
```

2次元セル座標から連続配列のセルインデックスへの変換は次式とする。

```text
cellIndex = localCellCoordinateZ * gridCellCountX
          + localCellCoordinateX
```

セルサイズにはCPU基準実装と同様に有効半径を使用する。固定グリッドの範囲は、2層の境界粒子を含むようC#側で計算する。

### セル登録の検証結果

2026年9月20日時点で、3×2セルの固定グリッドへ5個のテスト粒子を登録し、次の項目をUnity Editor上で確認した。

- セル粒子数の初期値がすべて0へクリアされること
- グリッド内の粒子が期待する一次元セルインデックスを保持すること
- 同じセルに属する複数粒子が`InterlockedAdd`によって正しく集計されること
- グリッド外の粒子に`uint`の最大値を無効セルインデックスとして設定すること

検証時の期待値は次のとおりだった。

```text
粒子ごとのセルインデックス: [0, 1, 1, 5, Invalid]
セルごとの粒子数          : [1, 2, 0, 0, 0, 1]
```

### セル開始位置の並列計算

セルごとの粒子数から、各セルが`SortedParticleIndices`内で使用する開始位置をExclusive Prefix Sumによって求める。

```text
粒子数: [1, 2, 0, 0, 0, 1]
開始位置: [0, 1, 3, 3, 3, 3]
```

GPU版ではBlelloch Scanを使用し、Up-Sweepで部分和を作成したあと、Down-Sweepで各要素へ開始位置を配る。

最初の実装では1スレッドグループを128スレッドとし、各スレッドが2セルを共有メモリへ読み込む。したがって、1グループ当たり最大256セルを処理する。

256セルを超える場合は、次の階層構造でグローバルな開始位置を完成させる。

```text
各グループ内で最大256セルをScan
  ↓
各グループの合計値を保存
  ↓
グループ合計をScan
  ↓
各セルの部分Scan結果へグループ開始位置を加算
```

Scanの途中結果には`groupshared`メモリを使用する。同じグループ内のスレッドが共有する値を次の段階で安全に参照できるよう、各段階の間で`GroupMemoryBarrierWithGroupSync`を実行する。

### グループ内部分Scanの検証結果

2026年9月22日時点で、8セルの粒子数を1グループ内でScanし、Exclusive Prefix Sumとグループ合計が一致することをUnity Editor上で確認した。

```text
セル粒子数      : [1, 2, 0, 1, 3, 0, 1, 2]
セル開始位置    : [0, 1, 3, 3, 4, 7, 7, 8]
グループ粒子合計: 10
```

この検証により、共有メモリへの読み込み、Up-Sweep、ルートの初期化、Down-Sweep、および結果の書き戻しが1グループ内で正常に機能することを確認した。

### グループ合計Scanの検証結果

2026年9月22日時点で、3個のScanグループが保持する粒子数合計を再度Scanし、各グループの開始位置が一致することをUnity Editor上で確認した。

```text
グループ粒子数合計: [400, 350, 120]
グループ開始位置  : [0, 400, 750]
```

この段階ではグループ数を最大256に制限する。1グループが最大256セルを担当するため、最大65,536セルまで扱える。現在想定する約2,000セルに対して十分な範囲である。

### 複数グループScanの統合検証

2026年9月22日時点で、600セルを3個のScanグループへ分割し、次の3カーネルを連続実行した結果がCPU上で計算したExclusive Prefix Sumと全要素で一致することを確認した。

```text
1. 各グループ内でセル粒子数を部分Scan
2. 3個のグループ合計をScan
3. 各セルの部分開始位置へグループ開始位置を加算
```

テスト条件は次のとおりだった。

```text

Scanグループ数 : 3
粒子数合計      : 1,200
```

これにより、256セルの境界を越えるグリッドでも、各セルの粒子インデックス格納開始位置をグリッド全体で正しく計算できることを確認した。

### GPU空間グリッド構築の統合検証

2026年9月22日時点で、粒子登録から粒子インデックスのセル単位整列までを連続実行し、GPU空間グリッドが正しく構築されることをUnity Editor上で確認した。

```text
粒子の所属セル計算
  ↓
セル粒子数の集計
  ↓
セル開始位置のScan
  ↓
セル書き込み位置の初期化
  ↓

```

テストでは5粒子のうち4粒子を6セルのグリッド内へ配置し、1粒子をグリッド外へ配置した。次の結果を確認した。

- グリッド内粒子の所属セルが期待値と一致すること
- グリッド外粒子が無効セルとして除外されること
- セル粒子数とセル開始位置が一致すること
- 書き込み位置が`開始位置 + 粒子数`まで進むこと
- 同一セル内の順序に依存せず、期待する粒子インデックス集合が格納されること

### GPU密度計算の統合検証

2026年9月23日時点で、構築済みのGPU空間グリッドから各粒子の所属セルと周囲8セルを探索し、Poly6カーネルによって密度相当量と流体深さを計算できることを確認した。

有効半径は粒子ごとの値ではなく、シミュレーション全体で共通の`_EffectiveRadius`を使用する。GPU粒子構造体内の`EffectiveRadius`は、CPU・GPU間の48 bytesのデータ配置を維持するため現時点では残している。

テストではCPU版`SphSweKernel.EvaluatePoly6`による全粒子探索の結果を期待値とし、GPU版の計算結果と比較した。グリッド外の粒子は近傍候補から除外し、密度と流体深さが全粒子で許容誤差`0.0001`以内に一致することをUnity Editor上で確認した。

## GPU側のフレーム時間管理

サブステップごとにCFL時間刻みをCPUへ読み戻すと、CPUがGPUの完了を待つ同期が発生する。連続実行では、時間状態とサブステップ継続判定をGPU側へ保持する。

```text
描画フレーム開始
  ↓
Time.deltaTimeを未処理時間へ加算
  ↓
最大サブステップ回数分のDispatchを登録
  ├─ 未処理時間と回数上限から実行可否を判定
  ├─ 空間グリッド、密度、加速度を計算
  ├─ CFL時間刻みを計算
  ├─ CFL時間刻みと未処理時間から実時間刻みを確定
  ├─ 粒子を積分
  └─ 進めた時間を減算して完了回数を加算
```

時間状態は次の4値を持つ。

```text
AccumulatedSimulationTime
CurrentSimulationTimeStep
CompletedSubstepCount
IsSimulationSubstepActive
```

C#とHLSLの双方で`float`2個と`uint`2個を同じ順序で配置し、Structured Bufferのstrideを16 bytesとする。C#側では`StructLayout(LayoutKind.Sequential, Pack = 4)`によって宣言順と4 bytes境界を明示する。構造体内の`const Stride`はインスタンスデータに含まれないため、GPUへ転送する16 bytesの配置には影響しない。

CPUは1フレーム当たり最大20回分のDispatchを登録する。必要な時間を進め終えた後は`IsSimulationSubstepActive`を`0`とし、各計算カーネルの先頭で早期終了する。これにより、サブステップごとのGPUからCPUへの読み戻しを避ける。

未処理時間には上限を設ける。処理落ちした時間を無制限に蓄積すると、過去の時間へ追いつくための計算がさらにフレームを遅らせるためである。

2026年9月28日時点で、GPU時間状態、フレーム開始、サブステップ開始、実時間刻み確定、粒子積分、サブステップ完了およびUpdate駆動ループを実装済みである。Editorでは実行後の時間状態を`AsyncGPUReadback`で一度だけ読み戻し、次の不変条件を検証する。

- 蓄積時間が有限かつ`0`以上、設定上限以下であること
- サブステップ完了後の現在時間刻みが`0`であること
- 完了回数が最大サブステップ数以下であること
- 予約されたサブステップが完了して非アクティブであること

Unity Editor上で次の成功ログを確認した。

```text
GPU simulation time state validation passed. Accumulated: 0, Completed steps: 5.
```

この結果では、描画フレームの経過時間を5サブステップで消費し、未処理時間が`0`となった。完了回数は設定上限20以下であり、時間状態の基本的な更新が正常に完了した。

### Group Barrierを使用するカーネルの非アクティブ処理

`GroupMemoryBarrierWithGroupSync`を使用するカーネルでは、Barrierより前に動的な条件で一部スレッドが早期リターンする可能性を作ってはならない。全スレッドがBarrierへ到達しない場合、Compute Shaderカーネルが無効になるためである。

この制約により、次の3カーネルには`IsSimulationSubstepInactive()`による先頭の早期リターンを置かない。

- `ScanCellParticleCountsByGroup`
- `ScanCellParticleCountGroupSums`
- `CalculateMinimumTimeStep`

非アクティブ時の追加最適化を行う場合も、グループ内の全スレッドをBarrierへ到達させたまま、入力値をゼロまたは既定値にする、重い粒子計算だけを省略する、結果書き込みだけを抑止する、といった構造にする必要がある。

### 連続実行後のGPU粒子検証

GPUフレームループ後の粒子バッファを`AsyncGPUReadback`で一度だけ読み戻し、次を検証するEditor専用処理を追加した。

- 位置、速度、加速度、密度および流体深さが有限値であること
- 流体粒子がシミュレーション領域内に収まること
- 境界粒子の位置と速度が初期状態から変化しないこと
- 初期状態から位置または速度が変化した流体粒子数を診断情報として報告すること

一様な静止状態では流体粒子が動かないことも正しいため、移動粒子数が`0`であること自体は失敗条件にしない。

2026年9月28日、Unity Editor上で次の成功ログを確認した。

```text
GPU continuous particle validation passed. Particle count: 985, moved fluid particles: 24.
```

全985粒子が検証条件を満たし、そのうち流体粒子24個の位置または速度が初期状態から変化した。これにより、GPUフレームループが時間状態を更新するだけでなく、確定した実時間刻みを使用して粒子積分まで継続実行していることを確認した。

# フレーム駆動のシミュレーションループ

## 背景

当初はUnityの`FixedUpdate`一回につき、`Time.fixedDeltaTime`を複数のサブステップへ分割してSPH-SWEを計算していた。

Profilerでは、重い描画フレーム中にUnityが遅れを取り戻すため、`FixedUpdate`を17回連続実行している状態を確認した。各`FixedUpdate`が10サブステップを実行したため、一描画フレーム中の合計は170サブステップとなった。

```text
シミュレーション処理が重い
↓
描画フレームが遅れる
↓
UnityがFixedUpdateを追加実行する
↓
サブステップ数が増加する
↓
さらに描画フレームが遅れる
```

これは、計算の遅れを取り戻そうとする処理が新たな遅れを作る、キャッチアップの悪循環である。

## 採用した設計

SPH-SWEの実行起点を`FixedUpdate`から`Update`へ変更した。

```text
変更前:
FixedUpdateが呼ばれるたびに最大20サブステップ

変更後:
一描画フレームのUpdateにつき最大20サブステップ
```

`Update`では`Time.deltaTime`を未処理時間へ加算する。ただし、蓄積可能な時間と一フレーム中のサブステップ数には上限を設ける。

```text
Maximum Accumulated Simulation Time = 0.04秒
Maximum Simulation Substep Count = 20
Maximum Simulation Time Step = 0.002秒
```

現在の設定では、一描画フレーム中に進められるシミュレーション時間の上限は次のとおり。

$$
20\times0.002=0.04\ \mathrm{s}
$$

## 処理落ち時の方針

実時間に追いつくために無制限に計算を増やすことはしない。

一フレームの処理能力を超えた場合は、次の優先順位を採用する。

1. 一フレーム当たりの計算量を上限以内に保つ。
2. 許容範囲の未処理時間だけ次のフレームへ持ち越す。
3. 蓄積上限を超える時間は破棄し、シミュレーション時間が実時間より遅れることを許容する。

ゲーム全体を長時間停止させて完全に実時間へ追いつくより、操作と描画を継続できる方を優先する。

## 変更後の診断結果

変更後の診断では次の値を確認した。

```text
Selected Time Step = 0.002000秒
Last Completed Substep Count = 20
Estimated Required Substep Count = 20
```

以前確認された一描画フレーム中の170サブステップは、構造上発生しなくなった。

ただし、20サブステップ自体の計算負荷はまだ大きい。今回の変更は近傍探索を高速化するものではなく、負荷が自己増殖する問題を分離して抑止するものである。

次の最適化対象は、Profilerで最大の処理時間を占めた`SPH-SWE.CollectNeighbors`とする。
